# 策划 → 程序 · 交接手册

> 适用于本仓库：Unity 6000.6.4f1，规则基准在 `Assets/TuningLab`，数值在 `Assets/Resources/GameTuning.asset`，Issue 在 GitHub `sfher/hui`。
>
> 硬约定见 [AGENTS.md](../../AGENTS.md)；Issue 用法见 [issue-tracker.md](issue-tracker.md)；标签见 [triage-labels.md](triage-labels.md)。

## 0. 一句话

**策划交付"可观测的规则"，程序交付"可复现的读数"。中间不靠口述。**

交接失败只有一种形态：两边各自有一套规则，且都觉得自己对。本仓库已经付过一次这个学费（[速度等级-基准与教训.md](../速度等级-基准与教训.md) 教训 ①），代价是冲刺和碰撞整套重做。

## 1. 谁定什么

| 东西 | 谁拍板 | 写在哪 | 什么时候算定 |
| --- | --- | --- | --- |
| 规则集（允许什么、不允许什么） | 策划 | `docs/` + ADR | ADR 合并进 `main` |
| 数值（4 格、0.5 s、Vp 门槛） | 策划自己拖 | `GameTuning.asset` / 实验台滑块 | 写进 Issue 的一条"定稿"评论 |
| 实现方式（数据结构、算法、改哪个文件） | 程序 | 代码 + PR | PR 合并 |
| 读数（怎么证明它对了） | 策划提，程序确认可测 | Issue 的验收清单 | 清单全勾 |
| 不可逆的决策 | 共同，程序执笔 | `docs/adr/` | ADR 状态改成"已接受" |

三条边界：

- 策划**不要**指定实现（"用状态机""加个协程"）。要说的是约束（"同一物理步内可复现""不能靠帧率"）。
- 程序**不要**在没有四件套的情况下开工。缺了就是缺了，退回 Issue 挂 `needs-info`。
- **ADR 是策划管得住程序的手段**，不只是程序的技术档案。拍完板就要求写进去，下次谁要改都得公开推翻。

## 2. 一条机制需求 = 四件套

缺一条，程序就会自由发挥；缺两条，就会做出你没要的东西。

```
触发：什么条件下发生。写清边界 —— ≥ 还是 >，恰好相等算哪边。
效果：用格 / 速度 / 等级 / 秒描述。禁止形容词。
读数：在哪一栏能看出来（HUD 的哪一列、实验台的哪个数字、几步之内）。
反例：什么情况下必须不发生。这一条最重要，它是唯一能挡住"两套规则并行"的东西。
```

再加一项：**影响范围**（哪些关卡、哪些机关、哪些文档会被带塌）。没有影响范围的需求，等于把排查成本丢给程序。

例子（本仓库真实的一条）：

```
触发：B 冲刺撞上 A，且 A 沿碰撞轴的速度低于 v2 门槛（8 格，28.28）
效果：A 沿轴速度 = 撞击方碰撞前速度（20.12）；不给额外距离、不减速撞击方
读数：HUD 速度栏 20.12 / 折算 4.05 格 / 描边黄 v1
反例：A 不得出现 28.28；B 不得掉速；两人不得产生斜向速度
影响：L1 的 v2 破墙；绳 / 冰的挡位阈值；README 与策划案 §3
```

## 3. 交接流程（五步）

| 步 | 谁 | 产出 | 退出条件 |
| --- | --- | --- | --- |
| 1 立案 | 策划 | Issue（四件套 + 影响范围） | 程序确认"读数可测"，无歧义 |
| 2 原型 | 程序 | `TuningLab` 里的可拖参数版 | 策划能在 5 分钟内自己拖出"对的感觉" |
| 3 定稿 | 策划 | Issue 里一条"定稿：4 格 / 0.5 s / Vp≥800" | 数字唯一，程序写进 `GameTuning.asset` |
| 4 移植 | 程序 | 正式关卡 + 过期文档/ADR 同步 | `main` 上的关卡与实验台读数一致 |
| 5 验收 | 策划 | 在 PR 里按清单打勾 | 全勾才合；不勾就写清哪一条、期望多少、实际多少 |

两个原则：

- **先在实验台定，再进关卡。** 在关卡里调手感 = 每改一次都要重摆一遍地形。
- **定稿必须是一次性的一句话。** "看起来差不多了"不是定稿；下次再问又要重来。

## 4. 语言对照（最容易翻车的地方）

| 策划说 | 程序听到 | 应该写成 |
| --- | --- | --- |
| "撞飞出去" | 多远？多快？多久？ | "沿轴速度 = 20.12，走完 4 格，不额外加速" |
| "手感太飘" | ??? | "地面加速度 90 → 140，其余不动" |
| "有点滑" | ??? | "地面制动 30，松手后约 1.5 格停住" |
| "能穿过去" | 触发器还是穿墙 bug？ | "碰撞体设为触发器；离开后恢复实体" |
| "踩头能带着走" | ??? | "站在队友上时，目标速度 = 队友速度 + 自己的方向输入" |
| "跳不上这个台" | 关卡太高还是跳太低？ | "台高 2 格，跳高 2.2 格，实测能否站上去" |
| "太强了" | 哪个数值强？ | "冲刺位移 4 → 3.5 格，其余不动，只准改这一项" |

**形容词不是需求。** 一个形容词背后至少有一个数值和一条边界，找到它再提。

## 5. 给策划的五条禁令

1. **不要一条 Issue 塞多个互相依赖的规则。** 拆开，各自能单独验收。
2. **不要在聊天里改结论而不回 Issue。** 聊天里定的东西等于没定。
3. **不要拿旧场景 / 旧截图里的数值当参照。** 序列化字段会覆盖代码默认值（教训 ②），以 `GameTuning.asset` 为准。
4. **不要用"先做出来看看"代替规则。** 尤其是碰撞手感：它会带塌全部关卡。
5. **不要在验收没打勾时同意合并。** "先合进去以后再说"= 以后永远不说。

## 6. 模板

### 6.1 Issue（`gh issue create` 的正文）

```md
## 目标

（一句话：玩家应该能/不能做什么）

## 规则

- 触发：
- 效果：
- 读数：
- 反例：

## 影响范围

- 关卡：L1 …
- 机关：绳 / 冰 / 破墙 …
- 文档：策划案 §3、README、ADR-0004 …

## 待拍板

- [ ] …

## 不做

- …
```

### 6.2 定稿评论（策划发，程序照抄）

```md
定稿（YYYY-MM-DD）：
- 冲刺位移 = 4 格
- 充能 = 0.5 s
- 红热门槛 Vp ≥ 800（= 28.28²）
不做：不要给它加额外的 +1 级。
```

### 6.3 PR 描述（程序填，缺一栏就退回）

```md
## 改了什么

（一句话）

## 读数

| 项 | 期望 | 实测 |
| --- | --- | --- |
| 冲刺位移 | 4 格 | 4.02 格 |
| 撞后受击方速度 | 20.12 | 20.12 |

（截图 / 录屏）

## 测试

（跑了什么；跑不了就写"没跑，因为 …"）

## 文档

- [ ] 过期文档已标 superseded
- [ ] 新增/修改的规则已进 ADR
```

### 6.4 验收不通过（策划发，三句话说完）

```md
不通过：第 2 条。
期望：撞后 A 速度 20.12（v1）；实际：28.28（v2）。
先别改规则，先把这一条对齐。
```

## 7. 冲突与返工

- **规则冲突** → 以 ADR 为准。没有 ADR 的，当天补一条，别口头裁决。
- **文档与代码冲突** → 以代码为准，但当天必须改文档。本仓库目前有 11 处这种冲突，清单在 [冲刺与对撞-现行规则.md](../冲刺与对撞-现行规则.md) §6。
- **发现两套规则并行** → 立刻停手，先定唯一基准。这是最贵的一种债，越晚停越贵。

## 8. 本仓库的现成零件

| 用途 | 怎么用 |
| --- | --- |
| 立案 / 追踪 | `gh issue create -R sfher/hui --title "…" --body-file body.md` |
| 分支 | `feat/` `fix/` `refactor/` `docs/`，不直接推 `main` |
| 规则基准 | `Assets/TuningLab`（菜单 **GameJam → Build Tuning Lab**），参数在 Inspector 与 HUD 滑块 |
| 数值资产 | `Assets/Resources/GameTuning.asset`，运行时覆盖序列化字段 |
| 正式关卡 | 从 Tuning Lab 派生（**GameJam → New Level From Tuning Lab**），再用 **GameJam → Tuning Lab Level Editor** 改 `LabLevel` 数据；不要手改 `TuningLab.unity` / `World.unity` |
| 测试 | Unity Test Runner（EditMode / PlayMode）；本机已装 6000.6.4f1，跑不了就直说 |

已知缺口：**冲刺与对撞没有自动化测试**，只有 HUD 手动验收。这条补上之前，每次改冲刺规则都要人工回归一遍。

## 9. 第一次交接的自检清单

开工前（策划自查）：

- [ ] 四件套齐全，边界写了 `≥` 还是 `>`
- [ ] 至少一条反例
- [ ] 影响范围列了关卡、机关、文档
- [ ] 验收能在 HUD 或实验台上读出来，不需要看代码
- [ ] 明确写了"不做"

合并前（双方一起看）：

- [ ] PR 里的实测读数与定稿数字一致
- [ ] 过期文档已标 superseded
- [ ] 实验台与正式关卡读数一致
- [ ] 测试补了，或写明为什么没有
